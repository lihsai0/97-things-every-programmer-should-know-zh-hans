# 三思后行

> “无论你正在做什么，谨慎行事，考虑后果。” 	--Anon

​	即使一个日程表在刚开始的时候看着特别的舒适，你也不能避免在某些时候感到压力很大。如果你不得不在“做好”和“做快”中选择，通常，在理解的基础上快速地做这件事是很有吸引力的，出现问题稍后再回来修复它。当你对自己、你的团队、你的客户真心实意的许下这个承诺的时候，你是认真的。但是当下一次迭代带来新的问题时，你又会专注于那些新问题。这种被延期的工作被称为技术债务，它可不是你的朋友。具体地说，Martin Fowler在他的技术债务分类中将这种故意为之的技术债务称为技术债务，不应该与无意的技术债务混淆。

​	技术债务就像借钱：你可能在短期内从中受益，但你必须为其支付利息，直到完全还清。代码中的快捷方式使添加功能或重构代码变得更加困难。它们是缺陷和脆弱的测试用例的滋生地。你搁置它的时间越长，它就会变得越糟糕。等你终于抽出时间来进行最初的修复时，可能会有一大堆不太正确的设计选择叠加在最初的问题之上，使代码更难重构和修正。事实上，往往只有事情变得越来越糟糕，你必须去修复它的时候，你才会回去修复它。等到那个时候，问题往往已经变得很难解决，你可能也承担不起那么多时间或风险。

​	有时，你必须承担技术债务才能在截止日期之前完成任务或是实现某个特性的一小部分功能。试着不要把自己置于这种处境中，但如果情况需要，那就放手去做吧。但是（这是一个很重要的但是）你必须追踪技术债务，迅速偿还，否则情况会迅速恶化。一旦你为了妥协做了这种决定，写一个任务卡片或者在你的问题追踪系统中记录它，确保它不会被遗忘。

​	如果你计划在下一个迭代中偿还债务，那么成本将是极小的。不偿还债务将会产生利息，为了使成本可见这些利息应该被追踪。这将强调项目技术债务对业务价值的影响，并可以根据此确定偿还的优先次序。如何计算和跟踪这些利息将取决于特定的项目，但你必须追踪它。

​	尽可能地偿还技术债务，否者将会是一个非常不明智的决定。
